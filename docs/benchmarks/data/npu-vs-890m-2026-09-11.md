# NPU / Radeon 890M results CSV

These are the numeric tables for the September 2026
[NPU / Radeon 890M comparison](../npu-vs-890m.md):

- [24 aggregate cells](npu-vs-890m-2026-09-11.csv): four models × two backends ×
  three input lengths, with twelve requests per row.
- [96 block summaries](npu-vs-890m-2026-09-11-blocks.csv): the same cells split
  across four server runs, with three requests per row.
- [288 request observations](npu-vs-890m-2026-09-11-requests.csv): one row per
  captured request, retaining its block and repetition identifiers.

There are four counterbalanced blocks × three repetitions of the same prompt
per model/backend/input cell. These are descriptive timing repetitions on one
host, not twelve distinct quality tasks or independent machines. The request
table follows the captured schedule; no first request or outlier is removed.

| Column | Meaning |
|---|---|
| `model` | Model identifier used by the experiment |
| `backend` | `flm` = FastFlowLM/NPU; `vulkan` = llama.cpp/Radeon 890M |
| `nominal_tokens` | Full rendered input length; FLM Qwen reports four fewer native prefill tokens because of deferred controls |
| `block` | Zero-based block/server-run identifier (0–3), within each model/backend |
| `iteration` | Zero-based repetition at that input length within the server run (0–2); request table only |
| `n` | Number of requests summarized: 12 in cells, 3 in blocks; absent from request rows |
| `wall_s` | Client request time to completed stream, seconds; excludes server/model load |
| `first_answer_s` | Client latency to first answer text, seconds |
| `native_decode_tps` | Backend-reported decode rate; the native timing/count definitions differ between backends |
| `socket_mean_w` | Time-weighted mean firmware SocketPower over the request, watts |
| `socket_integral_j` | Integrated firmware SocketPower over the request, joules; not wall energy |

Metric columns hold medians in the cell/block tables and individual observations
in the request table. Each cell/block metric also has `_min` and `_max`
columns for its observed request range, not a confidence interval. All tables
keep full numeric precision so the rounded article values can be regenerated.
Medians of different fields are calculated separately: multiplying median
power by median time need not
reproduce the median integral.

Socket integrals use linear interpolation at client request boundaries and
trapezoidal integration of one-second-filtered samples. Model loading, idle
subtraction and phase-isolated energy are excluded. See the article for
sampling, boundary sensitivity, memory/thermal limits and the Gemma counter
correction. No per-second or per-token hardware-speed ratio can be inferred
by treating native backend counters as interchangeable.

## Reproduction record

The captured runtime reported llama.cpp build **10809 (`v0.4.0`)**, compiled
with **GNU 16.2.0**. The NPU device reported firmware **1.1.2.64**. Runtime,
kernel, Mesa and XRT package versions are listed in the article.

The following are the complete captured server argument lists, parameterized
only for the model identifier and local GGUF path. `MODEL_ID` is one of
`qwen3.5:2b`, `qwen3.5:4b`, `qwen3.6-moe:35b-a3b`, or `gemma4-it:e4b`;
`MODEL_GGUF` points to its paired file. Run only one server at a time on the
dedicated loopback port. These examples describe the capture, not permission
to interrupt another service or a complete benchmark-launch procedure.

```sh
llama-server -m "$MODEL_GGUF" --alias "$MODEL_ID" \
  --host 127.0.0.1 --port 52730 -dev Vulkan0 -ngl 99 \
  --parallel 1 --ctx-size 65536 -fa on -ctk f16 -ctv f16 \
  -b 2048 -ub 512 -t 12 -tb 12 --spec-type none \
  --cache-ram 0 --ctx-checkpoints 0 --reasoning off --jinja \
  --fit off --log-verbosity 4

/usr/bin/flm serve "$MODEL_ID" --host 127.0.0.1 --port 52730 \
  --ctx-len 65536 --prefill-chunk-len 4096 --pmode performance \
  --asr 0 --embed 0 --cors 0 --preemption 0
```

The launcher removed inherited `LLAMA_ARG_*` variables, explicitly selected
the FLM model root through `FLM_MODEL_PATH` and the registry through
`FLM_CONFIG_PATH`, and used a fresh private working directory. The other
environment variables were inherited but not exported. Consequently, these
arguments are not a capture of the complete process environment. The evidence
release must retain this limitation and provide the sanitized request bodies,
prompt construction, schedule, guards and loaded-artifact fingerprints.

Selected installed llama.cpp records report `USE="vulkan openmp flexiblas"`
(relevant enabled subset), with ROCm/CUDA disabled, and:

```text
CHOST=x86_64-pc-linux-gnu
CFLAGS=-O2 -pipe -march=znver5 -mtune=znver5 -mno-rdrnd -mno-rdseed
CXXFLAGS=-O2 -pipe -march=znver5 -mtune=znver5 -mno-rdrnd -mno-rdseed
LDFLAGS=-Wl,-O1 -Wl,--as-needed -Wl,-z,pack-relative-relocs
```

The runtime's build banner also says `debug`; this does not establish an
unoptimized build, and the saved flags above explicitly contain `-O2`.
These are selected package records, not a complete compiler-command replay.
FLM's ebuild also builds the host runtime from source; its installed record
contains the same host C/C++ flags. Those flags do not describe compilation
of the separately supplied NPU kernel binaries.
